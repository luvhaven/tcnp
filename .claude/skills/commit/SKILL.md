# Commit by intent

One commit is one reason to change. A reviewer reading `git log` should be able to
tell what each commit was *for* without opening the diff, and reverting one should
not drag unrelated work out with it.

The failure this skill exists to prevent is `git add -A && git commit -m "updates"`:
twelve files, six unrelated reasons, one message that describes none of them.

## The rule

**Group by the reason the change was made, not by the folder the file lives in.**

Two files in the same directory belong in different commits if they were changed
for different reasons. Two files in opposite corners of the repo belong in the
same commit if one cannot work without the other.

Ask of each changed file: *if I reverted this commit, what single thing stops
happening?* If the answer needs an "and", it is two commits.

## Procedure

### 1. Read the whole diff before staging anything

```bash
git status --short
git diff --stat
git diff            # actually read it, not just the stat
git diff --cached   # anything already staged
```

Never group from filenames alone. A file called `utils.ts` tells you nothing
about which of the session's six intents it served.

### 2. Assign every changed file to exactly one group

Write the grouping out before touching `git add`. A file that genuinely serves
two intents is a signal to split it by hunk (step 4), not to duplicate it.

Groups that usually stand alone:

- **Dependency and tooling installs** — lockfiles, vendored packages, config.
  Almost always its own commit; it is the one thing a reviewer skims rather than reads.
- **Foundation changes** — tokens, config, shared types. Everything downstream
  depends on them, so they land first.
- **A shared primitive** — one component and its direct call-site fallout.
- **One bug fix** — the fix and its test, nothing else.
- **Mechanical sweeps** — a rename, a formatting pass, a codemod. Never mix a
  sweep with hand-written logic; the sweep hides the logic in the diff.

### 3. Order the commits so each one builds

Dependencies first, dependents after. A commit that references a token added two
commits later is a commit that doesn't compile in isolation, which defeats
`git bisect` and makes the history a lie.

### 4. Stage precisely

Whole files:

```bash
git add path/one.ts path/two.ts
```

When one file carries two intents, split it by hunk. **`git add -p` is
interactive and unavailable here** — write the hunk to a patch and apply it to
the index instead:

```bash
git diff path/to/file.ts > /tmp/full.patch
# hand-edit the patch down to the hunks for this commit, then:
git apply --cached /tmp/onlythese.patch
```

Verify before every commit:

```bash
git diff --cached --stat   # exactly the files you intended
git diff --stat            # what is deliberately left for later commits
```

### 5. Write the message

```
<type>: <what changed, imperative, under ~70 chars>

<why it changed — the reasoning a reviewer cannot recover from the diff>
```

Types: `feat`, `fix`, `refactor`, `perf`, `a11y`, `style`, `docs`, `test`, `chore`, `build`.

The subject says what. The body says **why**, and only why — never restate the
diff in prose. "Renamed x to y" is worthless; "y is the name used in the API
docs, and the mismatch caused three support tickets" is the commit message.

Omit the body only when the subject genuinely exhausts the reasoning.

Match the repository's existing convention if it has one:

```bash
git log --oneline -20
```

End every commit message with:

```
Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>
```

### 6. Never commit these without asking

- Build artifacts regenerated by a build you ran (`public/sw.js`, `dist/`, `.next/`).
  Check `git status` for files you did not edit by hand and revert them.
- Secrets, `.env*`, credentials, tokens.
- Large vendored directories — offer `.gitignore` as the alternative first.
- Unrelated pre-existing changes that were already dirty when the session started.

### 7. Report

List the commits made, each with its file count, and state explicitly what was
left uncommitted and why.

## Before you finish

| Mistake | Fix |
| --- | --- |
| `git add -A` then one commit | Group by intent first; stage each group separately |
| Commit message restates the diff | Replace the body with the reasoning behind the change |
| A commit that does not build alone | Reorder so dependencies land first |
| Formatting sweep mixed with logic | Two commits; the sweep goes second |
| Build artifact swept in | `git checkout --` it before staging |
| "and" in the subject line | That "and" is the seam between two commits |
